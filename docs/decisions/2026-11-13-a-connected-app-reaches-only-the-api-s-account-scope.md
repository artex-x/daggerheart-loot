# 2026-11-13 - A connected app reaches only the API's account scope

- Task: `ai-mcp` (planner 2026-11-11 and 2026-11-12, owner 2026-11-13, implementer B5a).
- Decision: a reader connects an app or AI assistant through Supabase Auth's OAuth 2.1 server (PKCE, dynamic registration on, the consent page `#/connect/<id>`). A connected app gets one grant level: every action the app's UI has on the reader's lists, share links, requests, homebrew and print sets, by the RPCs and table writes the app uses (the "UI action coverage" of the task), and never sign-in, the account's deletion or the display settings.
- Decision: the database bounds the token. A Supabase OAuth access token is a normal `authenticated` JWT with `client_id` and `session_id` (no custom scopes; it also carries the email, the phone and the metadata, measured 2026-11-13), so its holder calls PostgREST directly, past the Worker. The PostgREST pre-request function `api_client_guard()` refuses such a token on every table and function outside the scope's list and when its session has no `auth.sessions` row (a revoke deletes it, so «Отключить» stops an unexpired token at once; the plain refresh endpoint refuses the client's refresh token, and the consent row stays with `revoked_at`, measured on the local stack 2026-11-14). Restrictive policies refuse it on `user_prefs` and `print_sets` (an embedded read never names their path) and on a Storage update or delete, and on an upload once its session has ended (Storage never runs the guard). Realtime never runs it either: a client token receives the `owner:<uid>` and `share:` broadcasts of the scope, and after a revoke a client token that has not expired can still join and receive them until it expires, at most an hour. A later operation that needs another name changes the guard in a new migration, with a plan review.
- Decision (owner, 2026-11-13): Auth is bounded by Supabase's fix supabase/auth#2898 (merged 2026-11-03, in 2.198.0-rc.38 and later). Measured on the test project before it is deployed, a client token sets the password, enrolls a factor, reads and approves another app's authorization, and lists and revokes grants. The consent page and both privacy pages state what is true with the fix. Production's OAuth server is switched on only after the probes P1-P8 answer PASS-BLOCKED on the hosted project; the database guard stays either way.
- Decision: the Worker relays only a token with `client_id`, keeps none and never sees a refresh token; the `/me` CORS allowlist is empty until a browser client is reviewed; sync by heads, commands with client ids and `If-Match`.
- Rejected: scope enforced by the Worker only (the token works without it); a per-client read-only level (needs a client table; Supabase has no custom scopes); the app's own session token on the API (it carries the whole account, sign-in and deletion included); `*` on `/me`; audience binding by a custom access token hook (it changes the app's own tokens); our own token layer minted by the Worker (abandoned 2026-11-13); release before Auth's fix with the consent text naming the takeover (the owner chose to wait for the fix).
