# 2026-11-18 - A batch read has its own path, and search rows carry a built summary

- Task: `api-discover` (owner scope 2026-11-14, taken as the recommended option while the owner was away; implementer, 2026-11-18).
- Decision: `GET /api/v1/records-by-id?ids=` (MCP `get_records`) reads 1-20 (10 since the decision below) catalog records in one call, each chunk once, and names the ids the catalog does not hold in `missing`. The cap is the search's default page and bounds one call to 20 chunk reads.
- Decision: a search row carries `summary`, a `{ ru, en }` line of at most 120 characters that the build derives from the record's `plain` text or stat line (`tools/api-data.mjs` `summaryOf`), only when the request asks for it. The build writes it to `apidata/summary/<n>.txt` (64 KB files, one line a record, in search order), and the worker reads only the files of the answered rows.
- Decision (owner, 2026-11-18): the summary is opt-in, `fields=summary` on `GET /api/v1/records` and the same string argument `fields: "summary"` on MCP `search_catalog`; any other value is a 400 that names `fields`. Without it the worker reads no summary file. Reason: at 3x the catalog a cold `q=кольцо&limit=50` with summaries costs 11.5-12.1 ms service CPU and a cold two-word query 10.3-10.8 ms, past the 10 ms free-plan limit, and the default search must keep its old cold cost. The name `fields` (a list of extra row fields, today one value) leaves room for another opt-in field without a new parameter; it is a string on both adapters because the MCP adapter takes an argument as its query parameter's string or integer, and a boolean `summary: true` would need a type the REST query does not have. The MCP instructions tell a client to ask for summaries only when it must see what the items do, and to read full text with `get_records`.
- Rejected: the owner's example `GET /api/v1/records?ids=` (one path would answer two formats, and the public MCP tools are one operation each; an `x-mcp-also` variant for public tools is machinery for one tool); `/api/v1/records/batch` (it collides with `/records/{id}`); a cap of 50 (the search's largest page, but 50 chunk reads and a long answer for an assistant's context); a cap of 10 (half a default page, for about 1 ms less CPU).
- Rejected: the summary inside the search shard lines (the shard is scanned with `indexOf` on every search: three times the bytes, and summary words would count toward the 3000-hit `too_broad` cap); a summary from the record chunks at request time (one chunk read a row, up to 50); search over descriptions (the owner decided on 2026-11-18 not to build it, for the CPU of the search path); a summary on every row by default (past 10 ms cold at 3x); a smaller `SUMMARY_MAX` or `BUDGET.summary` instead of the opt-in (shorter lines still cost a read and a split a file, and smaller files raise the read count toward the subrequest limit).
- Decision (owner, 2026-11-18): the cap falls from 20 to 10 ids, together with a cheaper read that decodes only the answered record lines of a chunk. Reason: the production reading of 20 ids in 20 chunks at `f8bb4808` was 41.5 ms cold and 24.7 ms burst p50 (Pages Metrics), about 2 ms per id and about 14 times the Node service reading, and a v1 cap may rise but never fall, so the cap starts low. This is the one exception to "a cap may rise, never fall" (`CONTRACTS.md` section 6, "Batch read"): the cap had shipped only hours before and no client was known. The cap was expected to return to 20; the later decision "The batch cap stays 10, and text search is not built" keeps it at 10. The rejected "cap of 10" above is the choice taken now.
- Evidence: `docs/specs/CONTRACTS.md` section 6, "Summary" and "Batch read"; `.claude/README.md`, "Quotas, recovery and failure" (the readings of 2026-11-18).
