# 2026-10-10 - A key the account does not hold becomes a derived key

- Superseded in part by "Each Save to my items press makes a new copy, also of a catalog record" (2026-10-21): a «Сохранить себе» item takes a new key per press; its cards keep derived keys.
- Task: `persist-9-item-share` (owner, 2026-10-08: keys never collide across accounts, Q9-11 A and Q9-12 A; planner, the hash and the section rule).
- Decision: keys are unique per owner, so an import or a save that kept another account's key let a list row draw the reader's own item while it linked the author's. Now a key the account holds stays; any other `hb_` key becomes `derivedKey(userId, key)` (`lib/homebrew.ts`): `hb_` and the 80 most significant bits of the FNV-1a 128 hash of `<userId>\n<key>` in base32. The homebrew file import maps every source, card and item key and every `hb_` reference so (a section's key follows its source); the lists file import names a held key, else a held derived key, else copies under the derived key (`withCopies`); «Сохранить себе» writes the copy and its cards under derived keys and relinks each row that links the author's item to the copy, the database moving the row's key. One reader and one key give one key on every import and save, so the same file again, a corrected converter file with «Обновить», the move to another account (homebrew first, then lists) and a second press all find their keys held.
- Rejected: a random new key with an account mark in the file (it broke the move to another account and the converter loop); a hash of the key alone (two readers would share a key); a page index that let a linked row shadow an own item (it disagreed with `recordFor`); an «Это мой файл» choice (a wrong press makes clashes).
- Accepted trade-off: an own backup brings back a deleted item under its derived key; a clash made before this stays, and a third importer of two such files gets one item for both; a pending purchase request line of a relinked row's old key draws the raw key and reads short; a save whose relink did not run offers the press again, which relinks the rows to the held copy, also to a copy imported from the author's file; the key does not hide which keys one account derived (FNV-1a inverts step by step).
- Evidence: the frozen schema descriptions (`import-v2.json`, `import-v3.json`, entry `source`) keep their published wording; `llms.txt` and `docs/specs/CONTRACTS.md` section 4 carry the rule.
