## Nits

1. `local` - `docs/specs/DEBT.md`, D83: "An account at the default limits is a third of the rows"
   is not correct. The request lines are a product of three limits: 50 lists x 10 pending
   requests x 100 lines = 50 000 at the defaults, against 1.35 million at 3x (1/27). The
   entries are 1/9 (5 000 against 45 000). Only the single-limit collections (items, cards,
   sources, print sets) are a third. The planner places D83 from this entry, so write the real
   ratio: "At the default limits the request lines are 1/27 and the entries 1/9 of this seed."
2. `deferred-scope` (the planner's D83 placement) - the `todo` case in
   `tests/db/delete-account.test.mjs` still runs on every `check:db`: `node:test` executes a
   `todo` test and ignores only its result. Each run pays the 3x seed (34-42 s) and the 4 s
   timeout for a known failure, on a gate that already runs past the 600 s tool cap. Options:
   (recommended) keep `todo` until the planner places D83 in the nearest migration batch, and
   name the cost in the D83 entry; or change it to `skip`, which saves about 45 s per run but
   stops the re-measurement.
3. `local` - `OwnerRequests.read()` advances `#appliedSeq` only when the requests part is ok,
   but it applies the notices part before that check. If a newer read answers first with
   failed requests and ok notices, an older read that answers second applies its older notices
   over the newer ones (a hidden notice can come back until the next read). Advance
   `#appliedSeq` when any part of the read applies (`r.ok || all.ok || one?.ok`). Today's
   code had no order guard at all, so this is not a regression.
4. `local` - `app.test.ts`, "falls back on a bad value and writes nothing back": the app starts
   on `ru`, `#/roll/std` and `list`, so the fallback values equal the shown values and the case
   passes even if a bad value were ignored. Set a good value first (for example `en`), then the
   bad one, and expect `ru`.
5. `local` - `tests/db/run.mjs` `cli()` and `tools/supabase/restore.mjs` `cli()` call
   `supabaseCli(env)`, which throws when no binary package is installed. The throw escapes
   `runSuite` as a stack trace with no `check:db: FAIL` line. `resetLocal` already catches it.
   Catch it once in `run.mjs` and print the message with `check:db: FAIL`.
6. `local` - `bytesText` in `tools/supabase/usage-lib.mjs` prints 999 950 to 999 999 bytes as
   `1000.0 kB`. Compare the rounded kB value with 1000, or accept it and say so in the JSDoc.
7. `local` - `handoff.md`, Deferred: "`SUPABASE_CLI` ... name it to the owner at closeout". This
   is a defect (`config.mjs` and `db-push.mjs` fail in a worktree with no `node_modules`), and

- Data loss and two-tab merge: no stored data can be lost. Every change is in memory or in
  what a read fetches. A `fresh` row below the held revision keeps the held row, and no path
  re-creates a row or a list under the same id with a lower revision (imports use `on conflict
  do nothing`; the `#unsure` create is sent again only when the read shows the row absent). A
