## Blockers

**B1. «В список» in the record dialog does nothing over a roll result (blocking).**

`RollResult.svelte` draws `<AddToList key={it.id}>`. `PickRow.svelte` draws `<AddToList key={it.id}>`
in the dialog. A press on the card's picture opens the dialog of that same record, and `RecordHost`
keeps the page mounted under it (`{@render children(openRecord)}`, then `RecordModal`). So two
instances share one key, and `open` is `app.menuFor === key` in both.

The trace of a press on the dialog's «В список»:

1. The delegated handler runs `toggle()`, and `app.menuFor` becomes the id.
2. The document listener `onDocumentClick` of the result's instance runs. `app.menuFor === mine` is
   true, the target is connected, and `root.contains(e.target)` is false.
3. That instance sets `app.menuFor = ''`. The menu closes in the same click.

Listener order does not matter: the instance that does not hold the target always clears the
value. The comment in `AddToList.svelte` says a press on another control is "never undone here".
That holds only while keys differ, and this batch is the first to give two mounted instances one key.

Effect: on all nine roll pages, at every width, signed in or signed out, the primary action of every
dialog opened from a result opens nothing. The picture is the only way into that dialog, so the
defect hits every such dialog. The old roll card had no add control, so this is a regression.

Why CI cannot catch it: case 3 presses the dialog's control over a table, `_roll_wondrous_modal`
reads the closed control only, and `rollResult.test.ts` opens the menu with no dialog.

Requested change:

- Give `AddToList` an open-menu identity apart from the record: for example an optional `slot`
  prop, default `key`, read by `open`, `toggle` and `onDocumentClick`.
- `RollResult` passes `slot="roll-{it.id}-{col ?? 0}"`. Keep `key={it.id}`, because `recordFor(key)`
  and the sign-in action read it (R1).
- Add a `rollResult.test.ts` case: open the picture, press the dialog's «В список», read
  `aria-expanded="true"`, one `.dropmenu` in the dialog and none behind it.
- Add the same press to case 90.

No golden moves.

## Risks

**R1. A sign-in from a result loses the roll and leaves `menuFor` set (blocking only by its one-line cost: fix it with B1).**

The roll is page memory, and `signInAfter` returns to `app.hash` unless `inModal` is set. A
signed-out reader rolls, presses «В список», then «+ Новый список», «Войти» and the provider. The
return draws `/roll/std` at `n = 1`. `#runPending` sets `menuFor` to a record that the page no longer
draws, unless that record is the one at row 1. Three results follow:

- Nothing opens, and the record the reader wanted is gone.
- No instance can clear `menuFor`.
- `Shell.svelte` reads `menuFor !== ''` as a hold, so up to 760 px the header stops hiding until the
  next navigation.

No stored data is lost, but `plan-5.md` standing check 2 does not name this path. It says only that
refusals are `AddToList`'s own. `inModal` already gives the right behavior: the return goes to the
record's own page, where the menu opens. Pass that behavior from `RollResult`; the prop's name may
need a change. Add a `rollResult.test.ts` case on `signInAfter`'s hash and key. No golden moves.

**R2. Opening a menu inside `.results` changes a live region (not blocking).**

`.results` is `role="status" aria-live="polite"`, as S7 asked, and `status` is atomic by default. This
batch puts the add menu and «Ещё» inside it, and each opens by inserting nodes. By the ARIA rules a
screen reader may then read the whole region again, up to four cards, after the first menu item.
Before this batch nothing opened inside the region. I did not test this with a screen reader, so the
effect is expected, not observed.

Recommended: a visually hidden status that names the rolled records, and no `role` on `.results`.
That moves about 40 `_roll_*` goldens, so it rides batch 6's re-seed as an acceptance line.
Trade-off: one more hidden element per page.
