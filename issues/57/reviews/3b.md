## Blockers

### B1. A tap in the header stops the header from hiding (blocking)

`Shell.svelte`, `.topbar.away:not(:focus-within)`. This rule answers any focus, not only keyboard focus. A press on a job link or the language switch leaves the focus in the header, because a navigation moves no focus and the header stays mounted. The brand link and «Войти» take the same path; I did not probe them. So the reader's next scroll sets `.away` and the rule cancels it.

Measured on `dist-test/` at 360x640, with a trusted `page.touchscreen.tap` under `hasTouch` and `isMobile`, then again with `page.mouse.click`. Both gave the same result:

| Step | `top` | `.away` | `y` | Focus | `:focus-within` | `:has(:focus-visible)` |
|---|---|---|---|---|---|---|
| Tap «Таблицы», then scroll down | 0 | true | 850 | `A:Таблицы` | true | not read at this step |
| Tap EN, then scroll down | 0 | true | 850 | `BUTTON:EN` | true | not read at this step |
| After the tap on «Таблицы», before the scroll | 0 | false | 0 | `A:Таблицы` | true | false |

Effect: the job tabs are the main way to move between pages on a phone. After such a tap the header stays on screen until the reader presses something else. This fails the first acceptance line ("Up to 760 px, on every page ... the header is out of the window"). I expect this on Android Chrome, the same engine as this probe. I expect no defect on iOS Safari, which does not focus a link or a button on a tap. No real device was checked.

Why no suite sees it: `d.click` calls `el.click()`, which moves no focus, and case 86 reaches the reveal only through `page.focus`.

Requested fix:

1. Change the selector to `.topbar.away:not(:has(:focus-visible))`. H5's reasons hold: it is still CSS, with no handler and no race. In the probe `:has(:focus-visible)` read false after a tap, and true after a script focus on a fresh page, so case 86's `page.focus` line keeps its meaning. `:has()` is already in use in `ListPage`, `RecordCard` and `TableRows`.
2. Add to case 86: a trusted `page.mouse.click` on `nav.tabs a[data-job="tables"]`, then a scroll down, then `hiddenNow`.
3. Add to case 86: a real Shift+Tab into the header from the first focusable control of `main`, then `shownNow`. My Shift+Tab from the search field stopped on «Ещё», so a keyboard stop in the header is not yet proved with the new selector.
4. Change "a focus inside" to "a keyboard focus inside" in `FEATURES.md` ("Chrome") and in `DESIGN.md` ("The Hidden Header Rule"), and update the comment over the rule in `Shell.svelte`. In the decision file, add the rejected `:focus-within` and its reason.

## Risks

### R1. The popup query walks the whole page on every scroll frame (not blocking, local)

This answers the question in handoff Notes, item 1. The port does throttle: `onscroll` runs `fn` at most once per frame, so `held()` does not run per event. The cost per frame is still real. A `querySelector` with no match walks every element, so it does scale with rows. The brief's "does not scale with rows" (Standing check 1) is wrong.

Measured on `/tables/eq_weapon` at 360x640 on this host: 8319 elements, 0.62 ms per `querySelector('[role="menu"], dialog[open]')`, against 0.0015 ms for `scrollHeight`. So this query is nearly all of the handler's measured read cost. A phone is slower by a factor that I did not measure. I saw no dropped frames, and I did not look for them.

In the same handler, `nextHeader` returns a new object on each read, so `head` invalidates and the `class:away` effect runs each frame with nothing to change.

Recommended: make `ScrollRead.held` a function that `nextHeader` calls only on a read that would flip the state, and return `s` when nothing changes. The query then runs on a few frames per gesture, not on every frame. Trade-off: while a hold is on, `turn` follows only on a would-be flip, so up to 9 px of travel can stay after a close. The `headerScroll.test.ts` table needs the matching edit. A smaller option: test `document.activeElement` before the query. That saves nothing in the common case with no hold.

### R2. `FIELD` holds `select`, which has no on-screen keyboard (not blocking, local)

The spec, the brief's guard and the comment over `FIELD` all say "text field", and the reason given is the on-screen keyboard. A `<select>` opens no keyboard, and I expect it to keep the focus after a pick. A reader who picks a value in `SourcePicker` and then scrolls would keep a frozen header until the next press elsewhere. I read this from the code and did not measure it. The list comes from the brief's S6, so the implementer followed it.

Requested: remove `select` from `FIELD`, or name it in `FEATURES.md` with its reason.
